# Scale 4 Scoped Route Resolution

> Status: architecture choice.
>
> This document answers:
>
> How does an ingress obtain a Route Program without storing or receiving the global pathlet graph?

## 1. Reject global pathlet dissemination

Pathlet Routing demonstrates that globally learned path fragments can give small forwarding tables, but its simple route-selection model still assumes that edge routers learn a network-wide pathlet map and compute routes over it. The paper explicitly notes that this control-plane map may be large, even if it can live in cheaper edge memory and be cached.

NetSynth rejects this as the default Scale-4 control model.

Moving global routing state out of a fast FIB and into ingress DRAM does not satisfy the stronger NetSynth goal of locality of knowledge and change.

## 2. Prior-art reconciliation

### SCION

SCION separates path exploration/registration from on-demand path lookup. A local control service recursively obtains required up/core/down path segments, caches remote lookup results, and returns segments for route construction.

NetSynth adopts the general principle:

> destination-specific path information is pulled on demand and cached, rather than permanently flooded to every source.

NetSynth does not adopt SCION's AS/ISD, beacon-security, or endpoint path-selection semantics.

### Hierarchical PCE

Hierarchical PCE defines Parent and Child Path Computation Elements. A parent maintains a map of child domains and their interconnections but does not know child-domain contents; child PCEs compute paths within their own domains.

NetSynth adopts this knowledge boundary and recursive-computation principle.

NetSynth does not adopt MPLS/GMPLS traffic-engineering semantics, administrative domains, or the exact PCEP protocols.

### Path-reporting oracles

Path-reporting distance oracles prove that path queries can be answered from sparse preprocessed structures with explicit size/stretch/query-time trade-offs.

They are relevant implementation tools for a Scope Route Service, not a NetSynth architectural object by themselves.

## 3. Architecture choice: push summaries, pull routes

Scale-4 control information has two different directions and lifetimes.

### Persistent push

~~~text
child Scope
    -> parent Scope
    Boundary Transit Graph / Scoped Transit Pathlets
~~~

Only the stable routing contract is pushed upward.

### On-demand pull

~~~text
ingress Route Compiler
    -> relevant Scope Route Services
    destination-specific route query
    -> Route Program
~~~

Destination-specific path information is not globally disseminated.

This is the central Scale-4 control-plane choice.

## 4. Logical Scope Route Service

Every Routing Scope owns a logical **Route Service**.

Its persistent knowledge is limited to:

- the BTGs exported by its immediate children;
- physical crossing links among immediate children / local boundary objects;
- its own Scope-level routing objects and policy/metric state.

It does not contain arbitrary descendant physical topology.

A Route Service is a logical control-plane function, not necessarily one centralized machine.

An implementation may replicate or distribute it inside the Scope. Replication/consistency cost must later be explicit, but this does not change its knowledge boundary.

## 5. Destination-independent persistent state

The Route Service stores only reusable destination-independent routing structure.

It does **not** keep a permanent entry for every remote final destination.

The destination-specific state created for a query is transient or cacheable at the requesting edge/control service.

This is the main way NetSynth avoids recreating a global destination FIB inside the control plane.

## 6. Finding the responsible computation scope

Given:

~~~text
source position s
Destination Locator D
~~~

the source networking layer can determine the lowest Routing Scope L whose lineage contains both source and destination.

This follows directly from the Structured Locator / source Scope lineage.

If source and destination remain inside the same immediate child of L, the query is delegated to that child instead.

Otherwise L is the first Scope that must make a cross-child routing decision.

## 7. Query-time Access Offers

The persistent BTG describes only boundary-to-boundary transit.

A source or final destination may lie inside a child Scope.

Therefore route setup may request temporary **Access Offers**.

### Source Access Offer

For a point s inside child C:

~~~text
s -> boundary b
cost
opaque realizable route object
~~~

for relevant b in B(C).

### Destination Access Offer

For destination d inside child C:

~~~text
boundary b -> d
cost
opaque realizable route object
~~~

for relevant b in B(C).

These offers are generated by C's Route Service from its own child-level knowledge.

They are query results, not permanent advertisements to C's parent.

The architecture does not require that every boundary be returned. A theory-backed local query structure may return a sparse sufficient candidate set, provided the resulting end-to-end guarantee is stated.

## 8. LCA-level route computation

For source and destination in different immediate children of L, the Route Service of L constructs a transient query graph containing:

- all immediate-child BTGs already owned by L;
- physical crossing links owned by L;
- source Access Offers;
- destination Access Offers.

It computes a route in this graph according to the selected route metric.

Because child BTGs are ordinary graph structures, the chosen route may:

- enter a child;
- leave it;
- later re-enter it;
- transit through children unrelated to the destination lineage.

Thus Scope hierarchy limits knowledge, not path geometry.

## 9. Recursive materialization

The LCA-level result is a sequence of:

- child STP invocations;
- Scope-owned crossing actions;
- source/destination Access Offer objects.

Each opaque child object can be recursively materialized by the child that owns it.

The result is a Route Program executable through the Transit Stack.

A parent never needs the descendant physical path.

## 10. Route query is not required to return exact shortest path

The query algorithm is allowed to return an approximate route.

Its guarantee depends on:

- which STPs are persistently exposed;
- how Access Offers are produced;
- which path-search/query structure is used inside each Scope.

Those are mathematical construction choices that require their own known bounds.

The architecture contract is only that every returned Route Program is physically realizable and its advertised cost is conservative.

## 11. Caching

A source-side/ingress Route Compiler may cache Route Programs and Access Offers.

Caching is important because communication is usually not one isolated packet.

But cached route state remains edge/control-plane state, not mandatory state in transit forwarders.

A cache entry must eventually be tied to the generations/validity of the pathlets it references.

The exact invalidation/lease mechanism is deferred to the dynamic-control design.

## 12. No global Route Service bottleneck is implied

The logical Route Service hierarchy does not require one global server.

A high-level Scope summary is intentionally small and slow-changing enough that its Route Service state may be:

- replicated at several control nodes;
- distributed among immediate children;
- cached below the Scope.

The architecture requirement is the knowledge boundary, not a single control endpoint.

How replication is performed is a later control-plane implementation question and must be measured rather than assumed free.

## 13. Control-plane bootstrap

Every child Scope has an explicit parent-control relationship.

Route requests can therefore move along the Scope-control hierarchy without requiring the requester to know arbitrary global controller addresses.

The exact transport/reliability mechanism for control traffic remains unresolved, but Scale 3 already requires control traffic to retain a progress guarantee under data-plane saturation.

## 14. Why this differs from compact hop-by-hop routing

Compact routing would place enough destination-oriented information at transit routers to choose the next hop without route setup.

NetSynth instead chooses:

~~~text
persistent:
    destination-independent Scope/pathlet state

on demand:
    destination-specific Route Program

packet:
    compiled coarse forwarding state
~~~

This spends setup latency and packet bits in order to minimize globally replicated destination-specific routing state.

Compact routing remains a mathematical baseline for judging whether this trade is sensible.

## 15. Why this differs from SCION

The closest architectural resemblance is SCION path lookup, but the semantics differ.

SCION uses AS/ISD path-segment classes and lets endpoints combine segments.

NetSynth uses recursively nested topology-derived Routing Scopes and their BTGs. The Route Program is compiled by the network-side routing function; application-visible path control is not a common-core requirement.

## 16. Failure/change behavior

An internal event that leaves an STP contract valid:
- remains hidden;
- does not invalidate Route Programs using that STP.

If an advertised STP or Access Offer dependency becomes invalid:
- the corresponding cached Route Program becomes stale;
- new route setup must obtain a replacement.

This means route-program invalidation is proportional to **used routing objects**, not every destination whose shortest path numerically changed.

That is an architecture hypothesis to validate later.

## 17. Minimal validation eventually required

Do not benchmark generic path-finding theory.

Validate only:

1. no Route Service reads descendant physical topology;
2. a route can be compiled recursively from BTGs + Access Offers;
3. every returned Route Program is physically executable;
4. arbitrary child leave/re-entry paths work;
5. destination-specific state is absent from unrelated persistent Scope state;
6. an internal STP reroute with unchanged contract does not invalidate cached Route Programs;
7. query/cache state and packet Route Program size are explicitly charged.

## 18. Next architecture question

Scale 4 now has a complete basic information path:

~~~text
physical topology
    -> Scope-local control
    -> child BTG/STP contract
    -> on-demand scoped route resolution
    -> Route Program
    -> Transit Stack forwarding
~~~

The next problem forced by this design is dynamic validity:

> How are STP contracts and cached Route Programs versioned, invalidated, repaired, and refreshed under asynchronous topology change without requiring globally synchronized epochs?

That question must first reconcile with:
- soft-state/lease systems;
- path-vector withdrawal/versioning;
- MPLS/SR label lifetime;
- SCION path expiration/revocation;
- dynamic routing / loop-free update literature.

Do not implement before that reconciliation.
